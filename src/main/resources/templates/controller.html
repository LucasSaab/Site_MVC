Camada Controller: mediação e roteamento

O Controller recebe as requisições HTTP, coordena o acesso ao Model e determina qual View comporá a resposta.

1. Fundamentação teórica

O Controller atua como mediador entre a interface e o domínio. Em Spring MVC, essa função é distribuída entre o DispatcherServlet, que implementa o padrão Front Controller, e os métodos de classes anotadas com @Controller, responsáveis pelo tratamento de cada rota.

Conceito Teórico: Inversão de Controle

A instância de MvcPaginasController não é criada pelo código da aplicação, e sim pelo contêiner do Spring, que também decide quando seus métodos serão invocados. O desenvolvedor declara o mapeamento por anotações e delega o fluxo de execução ao framework.

3. Anatomia de um método de rota

O método paginaModel ilustra as quatro responsabilidades típicas de um manipulador de requisição: mapeamento, consulta, publicação de atributos e seleção da View.

Observação Técnica: dois sentidos para “Model”

A camada Model é o domínio de dados (ConceitoMVC). O parâmetro Model model, do pacote org.springframework.ui, é apenas o contêiner de atributos que transporta informações do Controller até a View durante a requisição. Os nomes coincidem, mas os papéis são distintos.

O que ocorre no Servidor?

Durante a inicialização, o Spring instancia o Controller uma única vez (escopo singleton) e registra suas rotas no HandlerMapping. A cada requisição, o DispatcherServlet consulta esse registro e invoca o método correspondente.

5. Submissões POST e o padrão Post/Redirect/Get

Além de responder a consultas com @GetMapping, o Controller trata submissões de formulário com @PostMapping. O parâmetro anotado com @ModelAttribute recebe os dados enviados: o Spring instancia o objeto, converte os parâmetros da requisição pelo nome e invoca os métodos de escrita correspondentes (Data Binding no sentido View → Model).

Ao concluir o processamento, o método não devolve uma View: devolve "redirect:/projetos". Esse é o padrão Post/Redirect/Get (PRG), cuja sequência é:

  1. O navegador envia o formulário com POST /projetos/criar.
  2. O Controller processa o envio e altera o estado da aplicação.
  3. O servidor responde com um redirecionamento (status 302 ou 303) para GET /projetos.
  4. O navegador emite o GET e recebe o HTML atualizado (200 OK).
Conceito Teórico: por que redirecionar?

Se o POST respondesse diretamente com HTML, atualizar a página reenviaria o formulário e duplicaria o registro. Com o PRG, a última requisição do histórico é um GET, seguro e idempotente, que pode ser repetido sem efeitos colaterais. Os flash attributes (addFlashAttribute) preservam a mensagem de confirmação apenas durante esse redirecionamento.

Observação Técnica: aplicação prática

O módulo de gestão de projetos, apresentado em “Da teoria à prática” na página inicial, aplica esse padrão nas rotas /projetos/criar, /projetos/{id}/atualizar e /projetos/{id}/excluir.

6. @Controller e @RestController

Aprofundamento

A anotação @Controller declara um controlador tradicional, cujo método devolve o nome de uma View para renderização no servidor. A anotação @RestController declara um controlador de API: o valor retornado é escrito diretamente no corpo da resposta, em geral como JSON.

O que ocorre no Servidor?

Em um @Controller, o retorno String é interpretado como nome de View e entregue ao ViewResolver. Em um @RestController, o retorno é escrito no corpo da resposta por um HttpMessageConverter (o Jackson, no caso do JSON) e o ViewResolver não é consultado.

Observação Técnica

Este projeto utiliza @Controller porque estuda o padrão MVC com Server-Side Rendering. Em uma API REST, a camada View do MVC deixa de existir no servidor, e o JSON passa a ser a representação do Model.

7. Tratamento de exceções com @ControllerAdvice

Aprofundamento

A anotação @ControllerAdvice permite centralizar, em uma única classe, o tratamento de exceções de todos os controladores. Cada método anotado com @ExceptionHandler trata um tipo de exceção e devolve uma View ou uma resposta, evitando blocos try/catch repetidos. Para APIs, a variante @RestControllerAdvice escreve a resposta de erro diretamente no corpo.

Observação Técnica

O projeto não implementa um tratador global. Sem ele, uma exceção não tratada resulta na Whitelabel Error Page padrão do Spring Boot, com status 500, como ocorre quando um template referencia um fragmento inexistente.

8. Questões de fixação

Qual é o objetivo do padrão Post/Redirect/Get?

Evitar o reenvio acidental de formulários. Após processar o POST, o servidor responde com um redirecionamento e o navegador faz um GET; assim, atualizar a página repete apenas a consulta, e não a operação de escrita.

Qual é a diferença entre @Controller e @RestController?

O @Controller devolve o nome de uma View, renderizada no servidor como HTML. O @RestController equivale a @Controller mais @ResponseBody: o retorno é serializado diretamente no corpo da resposta, em geral como JSON, para consumo por APIs.
