2. Limitações da abordagem

Observação Técnica: volatilidade

Os dados residem no heap da JVM. Ao reiniciar a aplicação, a coleção retorna ao estado definido no construtor do Controller, pois não há persistência em disco.

O que ocorre no Servidor?

Como o Controller é um bean singleton, a mesma instância da lista é compartilhada por todas as requisições. A coleção utilizada não é thread-safe, o que é aceitável para demonstração com acesso apenas de leitura, mas inadequado quando há escrita concorrente.

3. Evolução para persistência real: Spring Data JPA

Aprofundamento

A transição para uma persistência real substitui a lista em memória por um banco de dados relacional. Com o Spring Data JPA, o Model passa a ser mapeado como entidade (@Entity) e o acesso aos dados é delegado a uma interface de repositório, cuja implementação o framework gera em tempo de execução. A adoção exige as dependências spring-boot-starter-data-jpa e um driver de banco, como H2 ou PostgreSQL.

Conceito Teórico: o papel do @Repository

A anotação @Repository marca a classe como componente da camada de persistência e habilita a tradução de exceções específicas do banco para a hierarquia DataAccessException do Spring. Em interfaces do Spring Data, ela é opcional: o framework as detecta pela herança de JpaRepository; mantê-la serve como marcação semântica da camada.

Observação Técnica: fora do escopo do MVC puro

O repositório é uma camada adicional ao tripé Model, View e Controller. Este projeto a omite de propósito para isolar o padrão estudado. Em aplicações reais, costuma-se acrescentar também uma camada de serviço entre o Controller e o repositório, que concentra as regras de negócio e as transações.
