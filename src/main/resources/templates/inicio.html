Model-View-Controller em aplicações web com Spring Boot

Estudo de caso de uma aplicação com Server-Side Rendering que separa estado, lógica de requisição e apresentação em três camadas com responsabilidades distintas e baixo acoplamento.

  • Java 17
  • Spring Boot 3
  • Thymeleaf
  • Bootstrap 5
  • Server-Side Rendering

3 instâncias de ConceitoMVC mantidas em memória pelo Controller

1. Fundamentação teórica

O padrão Model-View-Controller organiza uma aplicação interativa segundo o princípio da separação de responsabilidades (separation of concerns). Cada camada encapsula uma dimensão do problema e expõe a outras apenas o contrato necessário para a colaboração.

💡 Conceito Teórico: desacoplamento

A divisão em camadas reduz a dependência mútua entre componentes. A View pode ser redesenhada sem modificar a estrutura de dados, e a lógica de roteamento pode evoluir sem alterar o modelo de apresentação. O custo é a necessidade de um mecanismo explícito de comunicação entre as camadas.

CamadaArtefato no projetoResponsabilidadeDetalhamento
Model ConceitoMVC e List<ConceitoMVC> Representar o estado e os objetos de domínio da aplicação. Camada Model
View Templates HTML, Thymeleaf e Bootstrap Apresentar os dados recebidos, sem executar lógica de negócio. Camada View
Controller MvcPaginasController Receber requisições HTTP, consultar o Model e selecionar a View. Camada Controller

2. Ciclo de vida da requisição HTTP

O diagrama resume o fluxo de controle para uma requisição GET /model. Os quatro participantes principais aparecem na ordem em que atuam; a resposta retorna ao cliente ao final do processamento.

  1. ClienteGET /model
  2. Controller@GetMapping("/model")
  3. ModelList<ConceitoMVC>
  4. Viewtemplates/model.html

Etapas detalhadas

Percorra o ciclo etapa por etapa, com os botões ou com as setas do teclado.

  1. Etapa 1 de 8

    Requisição HTTP GET Cliente

    O navegador emite GET /model, recebido pelo conector do servidor Tomcat embarcado.

    GET /model HTTP/1.1

  2. Etapa 2 de 8

    Despacho pelo DispatcherServlet Controller

    Implementação do padrão Front Controller: consulta o HandlerMapping e identifica o método anotado com @GetMapping("/model").

    DispatcherServlet → HandlerMapping → paginaModel

  3. Etapa 3 de 8

    Invocação do método do Controller Controller

    O contêiner invoca paginaModel(Model model) na instância gerenciada pelo Spring.

    public String paginaModel(Model model) { ... }

  4. Etapa 4 de 8

    Consulta ao estado Model

    A lista em memória é filtrada com a Stream API, produzindo o subconjunto de objetos a ser exibido.

    listaConceitos.stream().filter(...).collect(...)

  5. Etapa 5 de 8

    Injeção de atributos Controller

    A instrução model.addAttribute("listaModel", apenasModel) publica o resultado no escopo da requisição, tornando-o acessível ao template.

    model.addAttribute("listaModel", apenasModel);

  6. Etapa 6 de 8

    Resolução da View Controller

    O método retorna o nome lógico "model"; o ViewResolver o associa ao arquivo templates/model.html.

    return "model";   // → templates/model.html

  7. Etapa 7 de 8

    Renderização no servidor View

    O Thymeleaf avalia th:each e th:text (Data Binding), substituindo as expressões pelos valores do Model e gerando HTML estático.

    <div th:each="c : ${listaModel}"> ... </div>

  8. Etapa 8 de 8

    Resposta HTTP Cliente

    O servidor envia o documento com status 200 OK; o navegador apenas interpreta o HTML recebido.

    HTTP/1.1 200 OK
    🔍 O que ocorre no Servidor?

    Toda a composição do documento acontece antes do envio. Não há chamada assíncrona nem montagem de interface no cliente: o resultado do lifecycle da requisição é uma página HTML completa.

    3. Organização do projeto

    A estrutura de diretórios reflete a separação das camadas: o pacote model, o pacote controller e o diretório de templates correspondem, respectivamente, ao M, ao C e ao V.

    ⚠️ Observação Técnica

    O projeto adota MVC puro de forma deliberada: não há camada de serviço, repositório nem API REST. Essa restrição isola o padrão como objeto de estudo, ao custo de concentrar no Controller o acesso aos dados.

    4. Questões de fixação

    Por que o Controller não deve gerar HTML diretamente?

    Porque acoplaria o roteamento à apresentação, violando a separação de responsabilidades. A mudança de layout exigiria alterar código Java, e o teste isolado de cada camada tornar-se-ia mais difícil.

    Em que sentido a aplicação implementa Server-Side Rendering?

    O HTML final é produzido no servidor pelo Thymeleaf a cada requisição, combinando o template com os atributos do Model. O cliente recebe o documento pronto e não executa lógica de montagem.

    Qual é a função do método addAttribute?

    Registrar pares nome-valor no contêiner de atributos da requisição. É o mecanismo pelo qual o Controller transfere dados à View, que os acessa por nome nas expressões ${...}.
