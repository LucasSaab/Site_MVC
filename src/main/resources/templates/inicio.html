1. Fundamentação teórica

O padrão Model-View-Controller organiza uma aplicação interativa segundo o princípio da separação de responsabilidades (separation of concerns). Cada camada encapsula uma dimensão do problema e expõe a outras apenas o contrato necessário para a colaboração.

Conceito Teórico: desacoplamento

A divisão em camadas reduz a dependência mútua entre componentes. A View pode ser redesenhada sem modificar a estrutura de dados, e a lógica de roteamento pode evoluir sem alterar o modelo de apresentação. O custo é a necessidade de um mecanismo explícito de comunicação entre as camadas.

View Templates HTML, Thymeleaf e Bootstrap Apresentar os dados recebidos, sem executar lógica de negócio. Camada View

1.1 MVC clássico e Web MVC (Spring)

A formulação original do padrão, associada a aplicações desktop, pressupõe uma View persistente que observa o Model e é notificada a cada alteração, segundo o padrão Observer. Na web, o protocolo HTTP é orientado a requisição e resposta e não mantém estado entre chamadas: não existe um canal permanente pelo qual o Model possa notificar a View. O Web MVC do Spring, também referido como arquitetura Model 2 na literatura de Java EE, reorganiza a colaboração em torno do Controller.

AspectoMVC clássico (desktop)Web MVC (Spring)
Notificação de mudançasO Model notifica a View diretamente (padrão Observer).Não há notificação: a View é produzida sob demanda a cada requisição.
Entrada do usuárioEventos da interface gráfica, tratados pelo Controller.Requisição HTTP (GET ou POST) recebida pelo DispatcherServlet e roteada ao Controller.
Ciclo de vida da ViewInstância persistente, atualizada de forma incremental.Efêmera: o HTML é gerado a cada requisição e descartado após a resposta.
Transporte dos dadosReferências a objetos no mesmo processo.Atributos no contêiner ui.Model (escopo da requisição), serializados como HTML na resposta.
Estado entre interaçõesMantido pela própria aplicação em execução.Protocolo sem estado: manter estado exige sessão, cookies ou armazenamento externo.

Observer versus requisição e resposta. No MVC clássico, o Model mantém uma lista de observadores e os notifica a cada mudança. No Web MVC, uma alteração do Model só chega à View quando uma nova requisição aciona o Controller e provoca nova renderização; para atualizações sem recarregar a página, recorre-se a chamadas assíncronas feitas por JavaScript.

O transporte de dados é mediado pelo Controller e pelo contêiner org.springframework.ui.Model: o Controller consulta o estado, publica atributos no escopo da requisição e o template os consome durante a renderização. Encerrada a resposta, esse contêiner é descartado.

O que ocorre no Servidor?

Toda a composição do documento acontece antes do envio. Não há chamada assíncrona nem montagem de interface no cliente: o resultado do lifecycle da requisição é uma página HTML completa.

3. Organização do projeto

A estrutura de diretórios reflete a separação das camadas: o pacote model, o pacote controller e o diretório de templates correspondem, respectivamente, ao M, ao C e ao V.

Observação Técnica

O projeto adota MVC puro de forma deliberada: não há camada de serviço, repositório nem API REST. Essa restrição isola o padrão como objeto de estudo, ao custo de concentrar no Controller o acesso aos dados.

5. Questões de fixação

Por que o Controller não deve gerar HTML diretamente?

Porque acoplaria o roteamento à apresentação, violando a separação de responsabilidades. A mudança de layout exigiria alterar código Java, e o teste isolado de cada camada tornar-se-ia mais difícil.

Em que sentido a aplicação implementa Server-Side Rendering?

O HTML final é produzido no servidor pelo Thymeleaf a cada requisição, combinando o template com os atributos do Model. O cliente recebe o documento pronto e não executa lógica de montagem.

Qual é a função do método addAttribute?

Registrar pares nome-valor no contêiner de atributos da requisição. É o mecanismo pelo qual o Controller transfere dados à View, que os acessa por nome nas expressões ${...}.

Qual é a principal diferença entre o MVC clássico e o Web MVC do Spring?

No MVC clássico o Model notifica a View diretamente (Observer). No Web MVC não há notificação: a View é regenerada a cada requisição HTTP, e os dados chegam a ela por atributos injetados pelo Controller no ui.Model.
